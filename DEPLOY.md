# Развёртывание на Debian 12

Целевой сервер: **176.109.100.65**, пользователь **ivanchurakof**. Пароль SSH и
секреты приложения в архив не включены. Деплой состоит из двух репозиториев;
`npm run package:release` упаковывает оба, включая текущие локальные изменения.

Рабочий каталог текущей установки: `/home/ivanchurakof/apps/track-cafedra`.

## Что требуется от владельца

1. Добавить выданный публичный SSH-ключ в `~/.ssh/authorized_keys` пользователя
   `ivanchurakof`. Закрытый ключ остаётся на компьютере разработчика в
   `.deploy-keys/`, исключённом из Git, Docker и архива.
2. Обеспечить доступ root/sudo для однократной установки системных пакетов.
   При sudo с паролем административную команду ниже нужно выполнить в своей
   консоли. Передавать пароль в чат не требуется.
3. Открыть TCP 22, 80 и 443 в панели провайдера. PostgreSQL, Java и Next.js
   не публикуют порты наружу.
4. HTTPS можно включить непосредственно для IP через `deploy/enable-ip-https.sh`.
   Домен необязателен; если он нужен, направить A-запись на `176.109.100.65`.
5. Для Telegram указать токен и username из BotFather. Для регистрации по почте
   указать SMTP. Эти функции не нужны для первого запуска.
6. Предоставить исходную БД и файлы, если требуется перенос. По умолчанию
   создаётся новая БД со справочниками и администратором, без демонстрационных
   преподавателей.

Рекомендуется сервер с 4 ГБ RAM и свободным диском от 15 ГБ для сборок и образов.
Объём хранилища и резервных копий зависит от загружаемых файлов.

На текущем сервере обнаружены 1 ГБ RAM, около 1 ГБ swap и 6,7 ГБ свободного диска.
Поэтому образы собираются локально и передаются готовыми. Для первого запуска
используется `bash deploy/init-env.sh http://176.109.100.65 --small-server`:
PostgreSQL 128 МБ (shared_buffers 32 МБ), API 512 МБ, frontend 192 МБ, Nginx 64 МБ.
Бот выключен. Под нагрузкой потребуется увеличить RAM; сборку на сервере
с этими ресурсами выполнять не следует.

Для повторного выпуска готовых образов на Windows используйте:

```powershell
powershell -File scripts/build-release.ps1 -ReleaseTag release-002
```

Скрипт проверит frontend и Java API, соберёт Linux-образы и создаст в `dist/`
исходники, `images-release-002.tar` и SHA-256. На сервер передаются исходники и
образы. После проверки SHA-256 выполнить `docker load -i images-release-002.tar`,
сохранить прежний `.env.production`, установить `RELEASE_TAG=release-002`, затем
`bash deploy/compose.sh up --no-build --pull never -d --wait`. Telegram-образ
собирается отдельно, когда потребуется включить бот.

## 1. Архив и передача

На компьютере разработчика из корня проекта:

```powershell
npm ci
npm run lint
npm test -- --runInBand
npm run build
npm run package:release
```

В `dist/` появятся архив `track-cafedra-<дата>.tar.gz` и файл `.sha256`.
Пакет не содержит `.git`, `.env.local`, рабочих `.env`, SSH-ключей,
`node_modules`, `target`, `.next` и резервных копий. `deploy/RELEASE.json`
содержит версии обоих Git-репозиториев и перечень локальных изменений.

Пример передачи после добавления SSH-ключа (подставить имя архива):

```powershell
scp -i .deploy-keys/server_ed25519 dist/track-cafedra-<дата>.tar.gz dist/track-cafedra-<дата>.tar.gz.sha256 ivanchurakof@176.109.100.65:~/
ssh -i .deploy-keys/server_ed25519 ivanchurakof@176.109.100.65
```

На сервере:

```bash
sha256sum -c track-cafedra-<дата>.tar.gz.sha256
mkdir -p ~/apps
tar -xzf track-cafedra-<дата>.tar.gz -C ~/apps
cd ~/apps/track-cafedra-<дата>
```

## 2. Однократная настройка сервера

Из распакованного каталога, в консоли с sudo:

```bash
sudo bash deploy/bootstrap-debian.sh ivanchurakof 176.109.100.65
```

Скрипт ставит Docker Engine из официального Debian-репозитория Docker,
Compose, Nginx, OpenSSL и Certbot; создаёт отдельный виртуальный хост
`track-cafedra`, не заменяя другие сайты; добавляет пользователя в группу Docker.
Затем нужно переподключиться по SSH для активации группы.
Если имеется домен, вместо IP передать домен.

## 3. Секреты и окружение

```bash
bash deploy/init-env.sh http://176.109.100.65
```

Скрипт создаёт `deploy/.env.production` с правами 600 и случайными паролями
БД, администратора, JWT и общим секретом бота. Повторный запуск не заменяет
существующие секреты. Файл нельзя публиковать и пересоздавать при обновлении.

Прочитать пароль администратора можно в своей серверной консоли:

```bash
grep '^ADMIN_PASSWORD=' deploy/.env.production
```

Для HTTPS сразу укажите `https://ваш-домен` при генерации или измените
`PUBLIC_ORIGIN` в файле. Compose сам формирует CORS, ссылку подтверждения
регистрации и ссылку входа `/teacher/login`.

Для Telegram заполнить `TELEGRAM_BOT_USERNAME` (без @) и `TELEGRAM_BOT_TOKEN`.
Бот включается отдельным профилем. Username также встраивается во фронтенд
при сборке; пустое значение скрывает всплывающее приглашение.

Для email заполнить `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`,
`MAIL_FROM`, включить `MAIL_ENABLED=true`. В значениях с `$`, `#` или пробелами
использовать одинарные кавычки по синтаксису Compose .env. При выключенной почте
ссылки подтверждения появляются только в серверном логе; это режим отладки.

## 4. Сборка и запуск

```bash
bash deploy/compose.sh config --quiet
bash deploy/compose.sh build
bash deploy/compose.sh up -d --wait --wait-timeout 240
bash deploy/compose.sh ps
bash deploy/smoke-test.sh http://127.0.0.1:8090
```

Запускаются PostgreSQL, Java API, Next.js и внутренний Nginx.
На хосте доступен только `127.0.0.1:8090`, наружу трафик направляет системный
Nginx. Если меняется APP_PORT, нужно исправить порт и в системном Nginx.

Бот, после заполнения его параметров:

```bash
bash deploy/compose.sh --profile telegram up -d --build
bash deploy/compose.sh logs --tail=100 telegram-bot
```

Нельзя одновременно запускать два long-polling экземпляра одного бота.

## 5. HTTPS

Для текущего IP без домена:

```bash
sudo bash deploy/enable-ip-https.sh 176.109.100.65
```

Скрипт сохраняет исходные Nginx и `.env.production` в закрытый каталог
`backups/https-<дата>/`, устанавливает современный Certbot в `/opt/certbot`,
проверяет ACME-валидацию через staging и получает доверенный IP-сертификат
Let’s Encrypt. Сертификат действует 6 дней. Nginx обслуживает ACME-проверки
по HTTP и перенаправляет остальные HTTP-запросы на HTTPS.

Скрипт меняет только `PUBLIC_ORIGIN` на `https://176.109.100.65` в серверном
окружении и применяет его без пересборки образов. Пароли сохраняются.
Certbot systemd timer `track-cafedra-certbot.timer` проверяет продление дважды
в сутки и после успешного продления проверяет и перезагружает Nginx.
Старый Debian `certbot.timer` отключается, чтобы клиент 2.x не обрабатывал
конфигурацию нового клиента. Доступность TCP 80 и 443 должна сохраняться.

Проверка сертификата и автоматического продления:

```bash
sudo /opt/certbot/bin/certbot certificates
sudo /opt/certbot/bin/certbot renew --cert-name track-cafedra-ip --dry-run --run-deploy-hooks --no-random-sleep-on-renew
systemctl list-timers track-cafedra-certbot.timer
sudo journalctl -u track-cafedra-certbot.service --since '7 days ago'
bash deploy/smoke-test.sh https://176.109.100.65 176.109.100.65:443:127.0.0.1
```

Сертификат: `/etc/letsencrypt/live/track-cafedra-ip/fullchain.pem`;
закрытый ключ: `/etc/letsencrypt/live/track-cafedra-ip/privkey.pem`.
Резервные копии исходных настроек, содержащие секреты, доступны только root.
Скопировать их в общедоступное место или включать в архив релиза нельзя.
Дополнительный аргумент smoke-теста направляет запрос на loopback, сохраняя
проверку доверия сертификату и его соответствия публичному IP. Это позволяет
проверять HTTPS с самого сервера, где NAT hairpin публичного IP недоступен.

Для домена после настройки DNS потребуется изменить `server_name`, выпустить
отдельный сертификат через `/opt/certbot/bin/certbot --nginx -d ВАШ_ДОМЕН --redirect`
и задать соответствующий `PUBLIC_ORIGIN` в серверном окружении.

## 6. Приёмка

- `/admin`: войти с логином ADMIN_USERNAME и сгенерированным ADMIN_PASSWORD.
- Создать преподавателя с email и Telegram username, указать URL iCal.
- Проверить `/students`, `/teachers`, `/track`, `/track2`, `/new-track`.
- Проверить регистрацию по email, фото, скан КПК, выгрузки XLSX, пересдачи,
  дежурства, доступ преподавателя только к собственным записям.
- Smoke-тест проверяет также, что неверный пароль и анонимный `/api/auth/me`
  отклоняются с 401; демонстрационных API в Next.js больше нет.
- Камеру проверить в браузере по HTTPS; `/video.mp4` и `/TVP.MP4` необходимо
  предоставить отдельно, если эти ролики нужны на главной странице. В текущей
  установке Nginx раздаёт эти два файла из `/var/lib/track-cafedra/media/`:
  они сохраняются отдельно от Docker-образов и не теряются при обновлении frontend.
  Для замены загрузить под временным именем, затем переименовать в нужное;
  права 644, регистр имён важен.
- Проверить `/start` бота, если он включён.

## 7. Резервное копирование

```bash
bash deploy/backup.sh
```

Скрипт кратковременно останавливает работающие backend/frontend/бот, делает
`pg_dump` и архив файлового тома, проверяет архивы и возобновляет только ранее
работавшие приложения. Во время копирования сайт временно недоступен.
Результат в `backups/<UTC-дата>/`, признак полного успеха — файл `COMPLETE`.
Храните копии также вне сервера. Секреты из `.env.production` резервируйте отдельно.
Публичные видео из `/var/lib/track-cafedra/media/` в копию БД и файлового тома
не входят; их исходники сохраняются в локальной папке `public/`.

Восстановление выполняется вручную в отдельное проверочное окружение либо
в окно обслуживания: запустить только PostgreSQL, восстановить dump через
`pg_restore --clean --if-exists`, восстановить `storage.tar.gz` в файловый том
и назначить владельца UID 1001. До восстановления текущие данные копируются.
Не использовать `docker compose down -v`: команда удаляет постоянные тома.

## 8. Обновление и откат

1. Создать и скопировать согласованную резервную копию БД и файлов.
2. Сохранить текущие образы под отдельным RELEASE_TAG, например `release-001`.
   Этот тег в `.env.production` задаёт имя собираемых образов. Не перезаписывать
   теги предыдущих релизов; сохранять старый каталог приложения.
3. Распаковать новый архив в другой каталог, безопасно перенести тот же
   `deploy/.env.production`, указать новый RELEASE_TAG, очистить необязательный
   FRONTEND_RELEASE_TAG, собрать образы.
4. `bash deploy/compose.sh up -d --wait`, затем smoke-тест и ручная приёмка.
5. Для отката запустить `up -d --no-build` из предыдущего каталога с прежним тегом.
   Если менялась схема, сначала оценить совместимость; восстановление БД и файлов
   из копии может удалить изменения, сделанные после неё.

Имена томов фиксированы и совпадают с прежним backend Compose. Если тома уже
существуют, сначала проверить их содержимое, имя БД, пользователя и пароль.
POSTGRES_* не изменяют реквизиты уже инициализированной БД. Перед запуском на
старых данных проверить schema.sql: обязательные email и tg_username не должны
содержать NULL. Версионного инструмента миграций пока нет.

Для обновления только файлов `public/` без пересборки React и Java можно
использовать `deploy/apply-frontend-assets.sh КАТАЛОГ_ОБНОВЛЕНИЯ НОВЫЙ_ТЕГ`.
Каталог содержит изменённые файлы в `public/` и `deploy/frontend-assets.Dockerfile`.
Скрипт собирает небольшой слой поверх текущего frontend-образа, сохраняет
окружение в закрытую резервную копию и обновляет только frontend через
`FRONTEND_RELEASE_TAG`. При полном релизе этот параметр нужно очистить.

## 9. CI и диагностика

GitHub Actions проверяет фронтенд на Node 24. Для Java CI задать GitHub variable
`BACKEND_REPOSITORY=owner/repository`, необязательно `BACKEND_REF` (лучше SHA).
Для закрытого репозитория добавить read-only secret `BACKEND_READ_TOKEN`.
Локальные изменения backend необходимо отдельно закоммитить и отправить в его
репозиторий. Автоматического деплоя и публикации GitHub Pages больше нет.

```bash
bash deploy/compose.sh ps
bash deploy/compose.sh logs --tail=150 backend frontend gateway
bash deploy/compose.sh exec backend curl -fsS http://localhost:8080/actuator/health
sudo nginx -t
sudo journalctl -u nginx --since '10 minutes ago'
```

Пароль существующего администратора не меняется от замены ADMIN_PASSWORD.
Для него использовать API смены пароля. Данные в PostgreSQL и файлы живут
в отдельных постоянных томах; их удаление не требуется для обычного обновления.
